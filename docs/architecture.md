### What to consolidate

| Priority | Evidence | Core change and migration |
|---|---|---|
| 1. Reconcile core revisions | Windows pins the live-feed branch. Its three commits diverge from core main and overlap in `AprsProtocol.kt`, `AprsIsClient.kt`, and `RadioPacket.kt`. Its login version and redacted diagnostics are absent on main. | Reconcile position and RF envelope decoding with both branches' fixtures. Bring over the Windows login version and diagnostics behavior. Add captured or synthetic regression vectors without station credentials. Update the three app pins after running their compatibility suites. |
| 2. APRS-IS and station decoding | Standalone Android's `Main.java` handles the socket and login. `app.js:receive` parses TNC2 text, ordinary positions and addressed messages with regexes. Core already implements `AprsIsClient`, `AprsProtocol`, `AprsMessages`, `AprsFilters` and `AprsStationStore`. | Replace the Java socket and JS decoding with a small Kotlin bridge to the canonical client. Give the WebView typed station snapshots. Preserve the account, range filter and receive-only mode. Cover compressed positions, Mic-E, third-party packets, station aging and reconnect with shared fixtures. |
| 3. Reliable messaging | Android's `app.js:queueMessage/pump/receive` handles sequence, retry, ACK/REJ and dedup using WebView storage. Windows `ChatDatabase.kt` has account-scoped SQLite queries, retry state and durable history. Core `ChatSession.kt` already owns send/receive orchestration via `AprsMessageTransport` and `ChatRepository`. | Put delivery transitions, retry timing, wire-ID allocation rules and dedup keys in core. Give storage adapters atomic operations for pending claims, receive+dedup, ACK/REJ and outcome updates. Preserve full SSIDs, existing Android queues and history when migrating, verified-send gating, and retry after force-stop. Test stale ACKs, wire-ID wrap, account switches, reconnect and storage failures. |
| 4. GPS, beacon and radio | Windows `BeaconController.kt`, `GpsReceiver.kt`, `RadioPorts.kt`, `StandardQueries.kt` and `OperatingAutomation.kt` mix device I/O with packet formatting and decisions. Standalone Android emits location fixes through its Java bridge. Core already provides `BeaconEngine`, NMEA parsing, KISS/AX.25/AGW and RF routing policy. | Reuse those implementations. Extract remaining pure query response, telemetry formatting and scheduling decisions with injected fixes, capabilities and time. Retain device discovery, serial/BLE connections, dispatch and operating controls in the app adapters. |
| 5. Offline regional navigation | Android's `app.js` imports OSM XML, builds walk/drive graphs, snaps endpoints and routes by shortest distance. Windows uses `OfflineMaps.kt` for raster tile planning and has its own navigation search/UI. These are complementary capabilities. | For Android/Apple parity, extract the standalone graph, access rules, search and routing into an optional Kotlin module after fixtures cover one-way, foot access and disconnected routes. Keep raster tile storage/rendering, XML/file picker adapters and voice playback outside APRS protocol. Explicitly test offline operation and preserve the current limits around turn restrictions and rerouting. |

### Shared build and boundaries

Make the canonical core a Kotlin Multiplatform library that publishes a JVM/Android artifact and an Apple XCFramework. Keep pure policy in `commonMain`. Keep APRS-IS session behavior and Ktor in shared code unless a tested platform gap requires a byte-stream adapter. Export small, typed snapshots and commands to Swift. Keep maps, rendering, credentials, database/file I/O, location permissions, background lifecycle, device APIs and speech in app adapters. Version the public interfaces and pin all three apps to the same release after the branch reconciliation.

The current APRSERJi build compiles the pinned core sources directly with Kotlin/Native. This preserves the core's published JVM Gradle entry point while the Apple integration is proven. CI builds the framework, runs the common core tests on macOS, and compiles both app targets.

## Apple stack

| Need | Choice |
|---|---|
| App language | **Swift with SwiftUI** for iOS, iPadOS and macOS. **Kotlin Multiplatform** for the existing APRS engine. The Objective-C-compatible Kotlin/Native XCFramework gives Swift access to shared code. Direct C/C++ interop is available but would require a new engine or a separate library dependency. [SwiftUI](https://developer.apple.com/documentation/swiftui) · [Kotlin Apple frameworks](https://kotlinlang.org/docs/apple-framework.html) · [Swift C++ interop](https://www.swift.org/documentation/cxx-interop/) |
| Map and stations | **MapKit for SwiftUI** for the first milestone. Use `MKMapView` and `MKTileOverlay` if bundled raster tiles are needed. Evaluate MapLibre Native for vector offline maps on iOS. Its macOS implementation is mainly used for development, so validate desktop packaging before adopting it for both clients. [MapKit for SwiftUI](https://developer.apple.com/documentation/mapkit/mapkit-for-swiftui) · [MKTileOverlay](https://developer.apple.com/documentation/mapkit/mktileoverlay) · [MapLibre platform status](https://maplibre.org/maplibre-native/docs/book/platforms/index.html) |
| GPS, routing and speech | **Core Location** for device fixes, **AVSpeechSynthesizer** for spoken prompts, and a shared offline OSM graph for offline routing parity. **MKDirections** is an option for online routing and calls Apple's servers. Verify background behavior and permissions on each Apple platform. [Core Location](https://developer.apple.com/documentation/corelocation) · [Speech synthesis](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/) · [MKDirections](https://developer.apple.com/documentation/mapkit/mkdirections) |
| APRS-IS and TNCs | Reuse the Ktor APRS-IS client. **Network.framework** is available for native TCP endpoints if a platform adapter is needed. **Core Bluetooth** supports BLE TNC integrations with device-specific GATT services. Treat USB serial and classic Bluetooth radios as separate hardware compatibility tracks for iOS and macOS. [Ktor sockets](https://ktor.io/docs/server-sockets.html) · [NWConnection](https://developer.apple.com/documentation/network/nwconnection) · [Core Bluetooth](https://developer.apple.com/documentation/corebluetooth) |
| Durable chat | Use a SQLite adapter for per-account history and outbox transactions, and Keychain for APRS-IS passcodes if stored. Have the shared chat session own message delivery. [Keychain Services](https://developer.apple.com/documentation/security/keychain-services) |

The first milestone covers station receive and map display. The next milestones are durable two-way chat with a loopback APRS-IS fixture, then importing local OSM regions with offline search and walking/driving routes, then GPS following and voice cues. Device radio adapters can build on the existing shared KISS and AX.25 codecs.
